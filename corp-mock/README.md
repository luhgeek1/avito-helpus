# corp-mock: имитация корпоративных сервисов

Отдельный сервис, который изображает корпоративные системы демо-компании: сервис доступов,
сервис отсутствий, календарь, IT-поддержку, справочник и мессенджер. Интерфейс — MCP
(streamable HTTP, `POST /mcp`), как рекомендовали организаторы (№62 Q&A). Код mock не входит в
покрытие тестами (№72).

Бэкенд Орби подключается к нему через порт `CorpServices` (`backend/app/service/ports.py`) и
адаптер `McpCorpServices`. Чтобы подключить настоящий сервис (Jira Service Desk, внутренний сервис
доступов), пишется ещё один адаптер того же порта — домен и агент не меняются.

## Инструменты MCP

| Сервис | Инструменты |
|---|---|
| Доступы | `access_check`, `access_create_request`, `access_get_request`, `access_remind` |
| Отсутствия | `absence_balance`, `absence_create_request`, `absence_get_request` |
| Календарь | `calendar_events` |
| IT-поддержка | `itsupport_equipment`, `itsupport_create_ticket`, `itsupport_get_ticket` |
| Мессенджер | `messenger_post` |
| Управление демо | `demo_reset` — вернуть исходное состояние (его вызывает сброс демо в Орби) |
| Отмена | `request_cancel` — отменить ожидающую заявку; если решение уже принято, вернуть его |

Создание заявок идемпотентно по `idempotency_key`. Решение приходит через
`MOCK_APPROVAL_DELAY_SEC` секунд веб-хуком на `BUDDY_WEBHOOK_URL` с заголовками
`X-Corp-Timestamp` и `X-Corp-Signature: sha256=HMAC(CORP_WEBHOOK_SECRET, "<timestamp>.<body>")`.
Ответы и веб-хуки содержат исходный ключ. Новые номера короткие: `ACC-1042`, `ABS-2101`, `IT-3301`.
Счётчики сохраняются отдельно от заявок и не откатываются при обычном сбросе. Старые длинные
номера остаются доступными для чтения и повторов по прежнему ключу; новые выдаются без суффикса.
Повторное согласование не списывает дни повторно; остаток проверяется при принятии решения.
Напоминания дедуплицируются по ключу, отменённая заявка не будет автоматически одобрена.

Правила решений детерминированные:

- заявка на уровень «администрирование» отклоняется;
- обоснование короче 15 символов отклоняется;
- отсутствие дольше остатка дней отклоняется;
- остальные заявки одобряются.

## Управление для демо

| Запрос | Что делает |
|---|---|
| `GET /health` | проверка живости |
| `GET /admin/state` | заявки, сообщения в каналах, выданные доступы |
| `POST /admin/faults {"mode": "unavailable"}` | имитирует недоступность сервиса (`"ok"` возвращает) |
| `POST /admin/decide {"request_id": "<номер из /admin/state>", "status": "approved"}` | решение сразу, без ожидания |
| `POST /admin/reset` | очистить заявки, доступы и сообщения, сохранив счётчики номеров |
| `POST /admin/reset?reset_sequence=true` | также вернуть начальные номера; только после очистки БД API в согласованном сбросе |

Состояние (заявки, номера, выданные доступы, остатки дней, сообщения) хранится в памяти. Если задан
`CORP_STATE_FILE`, оно после каждого изменения пишется в этот файл и переживает перезапуск, а
ожидающие решения заявки заново ставятся в очередь. В обоих compose это `/data/state.json` на томе
`corp_state`. Рядом хранится `state.sequences.json`: следующий номер каждого сервиса резервируется
в нём до возврата заявки, запись атомарная с flush/fsync. Если удалить только state.json, нумерация
продолжится. При восстановлении старого снимка берётся максимум счётчика и уже сохранённых номеров;
это также поддерживает прежний длинный формат. Повреждённый файл счётчиков останавливает запуск,
а не молча начинает номера сначала. Хранилищем владеет один процесс corp-mock.

Для согласованного сброса обеих сторон используй `python deploy/reset_demo.py` из корня:
остановить API/worker → очистить БД API → очистить mock с `reset_sequence=true` → запустить API/worker.
Первая заявка Ани снова получит `ACC-1042`, первое отсутствие — `ABS-2101`.
При ошибке производители остаются остановленными. Обычный MCP `demo_reset` и административный
сброс из API не откатывают счётчики. Полностью новый стек также начинает с демо-номеров.

Потеря **всего** тома вместе с файлом счётчиков при сохранённой БД API — рассинхронизация:
без истории невозможно узнать ранее выданные номера. В этом случае API сохраняет защиту
по ключу и уникальному номеру: коллизия завершается failed с объяснением и уведомлением без retry.

## Запуск отдельно

```sh
uv sync
MOCK_APPROVAL_DELAY_SEC=5 uv run uvicorn corp_mock.server:app --port 8090
```
