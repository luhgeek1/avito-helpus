# Действия Орби в рабочем чате

**Статус:** реализовано и проверено. **Дата:** 16.11.2026.

## Основание и границы

Это развитие сценариев 002, 004, 005, 006, а не новая HR-система.
Основание: [ТЗ, разделы 04, 06/08, 07](../../docs/case/TASK.md),
[ответы Авито №28–33, 55, 61–63, 67, 79](../../docs/case/QA.md).
Пользователь попросил сделать действия доступными в пете и проверить соответствие ТЗ.
Все сотрудники, инструкции, остатки и сервисы в демонстрации синтетические.

## Путь пользователя

1. В рабочем чате (`/demo`, после входа) открыть «Действия».
2. Выбрать задачу, указать даты или описание.
3. Орби проверяет данные и права, показывает карточку с получателем и содержимым.
4. Пользователь подтверждает или отклоняет карточку. Подготовка формы ничего не отправляет.
5. Сервис возвращает номер и статус; они сохраняются и показываются в чате / заявках.
6. Итог обработки приходит уведомлением. Очередь не называется выполненным действием.

Главная `/` остаётся руководством по установке, её локальный помощник не выполняет рабочие действия.

## Сценарии и приёмка

| Сценарий | Ввод | Проверка и результат |
|---|---|---|
| Отпуск / отгул | Начало, конец | Остаток и важные встречи из MCP; предупреждения тестовых правил; подтверждение → ABS-номер → сохранённый статус |
| Больничный | Только даты | Уведомление в сервис отсутствий для HR; отпуск не списывается, учебный шаг отгула не закрывается |
| Доступ | Система / ресурс | Каталог с ACL; уровень и обоснование в редактируемой карточке; существующий полный сценарий 002 |
| Помощь IT | Описание неполадки | Карточка → IT-заявка; упоминание VPN или доступа в описании не меняет действие |
| Наставник | Вопрос / затруднение | Получатель из оргструктуры, карточка → эскалация → ответ уведомлением |
| Сообщение команде | Текст | Видны канал и текст; подтверждение → outbox → квитанция MCP → уведомление о доставке |
| Мои встречи | Период, по умолчанию 7 дней | Только календарь текущего пользователя, время МСК; никаких изменений встреч |
| Отмена заявки | Точный номер или UUID | Только своя открытая заявка; карточка → outbox → ответ сервиса; гонка с решением обрабатывается сервером |
| Напоминание | Номер заявки на доступ | Только отправленный доступ; подтверждение; ограничение повторов 20 часов |

Больничный здесь — организационное уведомление, **не медицинский документ и не согласование диагноза**.
Диагноз, медицинские вложения, выплаты и реквизиты не запрашиваются. Сервис сохраняет только
стандартный комментарий, даже если клиент прислал иной. Медицинское оформление остаётся вне бота.
Это выбранная граница прототипа, а не утверждение о регламентах Авито или юридическая инструкция.

## Инструменты и надёжность

- Те же инструменты для online и явно обозначенного offline-режима.
- `request_absence(sick_leave, start, end)` использует существующий порт и outbox.
- `control_request(reference, cancel|remind)` повторно находит свою заявку перед исполнением;
  в сохранённых аргументах карточки используется UUID, а не изменяемый внешний номер.
- `my_calendar(start_date?, end_date?)`: не более 31 календарного дня; пустой календарь и
  недоступный сервис дают понятный ответ, не выдуманные встречи.
- Карточка истекла / уже решена: существующий протокол 409; повторная отправка идемпотентна.
- Неизвестная / чужая заявка: одинаковое сообщение, без раскрытия владельца.
- Отправка в мессенджер подтверждается отдельной квитанцией. Повторы не дублируют сообщение
  и уведомление; после исчерпания попыток приходит уведомление об ошибке.
- При отказе сервиса UI показывает ошибку или ожидание; история и черновик сохраняются.

## Проверки

- Backend: `test_workplace_actions.py`, `test_requests_api.py`, `test_mcp_adapter.py`;
  реальные транзакции, протокол подтверждения, ACL и MCP, без внешней LLM.
- Frontend: `tests/orbi/actions.test.tsx`, существующие проверки чата и карточек.
- Браузер: desktop и phone, формы → подтверждение → реальный локальный API/MCP;
  отсутствие горизонтальной прокрутки, клавиатура, повторный клик закрывает чат.
- Полные проверки: `make check`, frontend typecheck/test/architecture/build, отчёт покрытия.

## Метрики

Время от открытия формы до зарегистрированной заявки; доля действий с результатом сервиса;
ошибки валидации и отмены карточек; время до решения по доступу; повторные обращения наставнику.
Эффект проверять A/B по существующей схеме аналитики, сравнивая одинаковые этапы стажировки.
