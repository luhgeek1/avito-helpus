# Спецификация: заявка на доступ (флагманский сценарий)

**Ветка**: `feat/ai-buddy-backend` · **Создано**: 14.11.2026 · **Статус**: реализуется

**Исходный запрос**: стажёр пишет «нужен доступ к репозиторию listings-api», Орби доводит до
выданного доступа: заявка создаётся в сервисе доступов (имитация через MCP), статус виден и
сохраняется, пункт плана закрывается после согласования.

## Пользовательские истории

### История 1. Доступ за один диалог (P1)

**Независимая проверка**: стажёр → чат «нужен доступ к Stash listings-api» → карточка → «Подтвердить»
→ заявка `ACC-…` в «Моих заявках» со статусом `submitted` → через `MOCK_APPROVAL_DELAY_SEC` веб-хук
`approved` → пункт плана `done`, уведомление «Доступ выдан» и следующий шаг.

**Сценарии приёмки**
1. **Дано** ресурс командный и стандартный, доступа нет, **когда** Орби готовит заявку, **тогда**
   карточка содержит ресурс, систему, уровень `read`, согласующего (владелец ресурса), обоснование
   и срок согласования; ничего ещё не отправлено.
2. **Когда** стажёр подтверждает, **тогда** бэкенд повторно проверяет права, создаёт заявку
   (`submitting`), сразу отправляет её в сервис доступов; при успехе статус `submitted` с внешним
   номером; карточка в чате и запись в «Моих заявках» показывают номер.
3. **Когда** приходит веб-хук `approved`, **тогда** заявка `approved`, связанный пункт плана `done`,
   стажёр получает уведомление и следующий шаг.
4. **Когда** стажёр меняет уровень или обоснование в карточке перед подтверждением, **тогда** в
   сервис уходят изменённые значения после повторной проверки.

### История 2. Исключения (P1)

1. Доступ уже есть → Орби сообщает уровень и дату выдачи, заявку не создаёт.
2. Уже есть заявка в работе на тот же ресурс → показывается существующая, дубль не создаётся.
3. Ресурс закрыт для роли (`restricted`, `confidential`) или неизвестен → «Такой ресурс я не нашёл
   или он недоступен для твоей роли», предложение спросить наставника. Существование ресурса не раскрывается.
4. Уровень `admin` для стажёра → недоступен, Орби предлагает `write` или вопрос наставнику.
5. Отказ (`rejected`) → причина из сервиса, пункт плана возвращается в `in_progress`, Орби предлагает
   исправить обоснование и подать снова.
6. Сервис недоступен при отправке → заявка остаётся `submitting`, воркер повторяет с экспоненциальной
   задержкой; после исчерпания попыток — `failed` и уведомление с советом.
7. Согласование дольше SLA (`ACCESS_SLA_HOURS`) → AI-крон напоминает стажёру и предлагает
   «Напомнить согласующему» (не чаще раза в сутки).
8. Стажёр отклоняет карточку → инструмент получает отказ, заявка не создаётся, в аудите — `rejected`.
9. Карточка не подтверждена за `ACTION_TTL_MIN` → `expired`, подтверждение отклоняется (409).

## Подтверждение, отправка и ошибки (по №67 Q&A)

| Шаг | Где | Что происходит |
|---|---|---|
| Подготовка | инструмент `request_access` до подтверждения | поиск ресурса по видимому каталогу, проверка доступа в сервисе (`access.check_access`), дубликатов, уровня; `ApprovalRequired` с карточкой |
| Карточка | `pending_actions` + SSE-часть `data-action` | ресурс, система, уровень, согласующий, обоснование, SLA, пометка «уйдёт в сервис доступов» |
| Решение | `POST /api/v1/chat/conversations/{id}/actions/{action_id}` | `approve` (с правками полей) или `reject`; повторное решение → 409 |
| Исполнение | инструмент с `tool_call_approved` | повторная проверка прав → заявка с ключом идемпотентности `tool_call_id` + событие outbox → немедленная отправка тем же обработчиком |
| Отправка в сервис | MCP `access.create_request` | `{employee_id, resource, level, justification, approver, idempotency_key}` |
| Результат | ответ сервиса | `{request_id: "ACC-1042", status: "pending_approval", sla_hours}` → заявка `submitted`, история статусов |
| Ошибка | таймаут, 5xx, сбой MCP | заявка `submitting`, повтор воркером; после `OUTBOX_MAX_ATTEMPTS` → `failed` + уведомление |
| Решение согласующего | веб-хук `POST /api/v1/integrations/corp/webhook` (HMAC, окно 5 мин) или сверка воркером | `approved`/`rejected` → заявка, план, уведомление, событие SSE |

## Требования

- **FR-001** Каталог ресурсов виден по ABAC: стандартные ресурсы компании и своей команды;
  `restricted` и `confidential` стажёру не показываются.
- **FR-002** Уровни: `read`, `write`, `admin`; стажёру разрешены `read` и `write`.
- **FR-003** Согласующий определяется ресурсом: владелец ресурса (руководитель команды) или DevOps.
- **FR-004** Заявка: статусы `submitting → submitted → approved | rejected`, `submitting → failed`,
  `submitted → cancelled`; каждое изменение — запись в истории с источником (пользователь, агент,
  воркер, веб-хук).
- **FR-005** Создание идемпотентно по ключу; повторная доставка веб-хука не меняет итог.
- **FR-006** Все решения по карточкам и созданные заявки пишутся в аудит.
- **FR-007** Есть путь без чата: `POST /api/v1/requests/access/preview` и `POST /api/v1/requests/access`
  используют тот же доменный сервис.

## Критерии успеха

- **SC-001** От запроса до созданной заявки ≤ 2 действий пользователя (сообщение + подтверждение).
- **SC-002** Время от запроса до выдачи доступа считается в аналитике (база для A/B).
- **SC-003** Ни одной заявки без подтверждения: интеграционный тест на отсутствие вызова сервиса до решения.
