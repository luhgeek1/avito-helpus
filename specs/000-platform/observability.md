# Наблюдаемость и синтетический Clickstream

**Основание:** кейс §06 (инфраструктурные рекомендации), §07 (<1 с для локальных операций), Q&A 75–77,
решения команды D-013…D-016. Это спецификация нашего прототипа, а не закрытого контракта Авито.

## Сценарий 1. Техническое состояние

1. Оператор включает профиль `observability`. Без профиля запуск для жюри прежний.
2. Prometheus собирает API внутри сети и отдельный процесс воркера на порту из Settings.
3. Grafana автоматически показывает «Орби — техника»: HTTP p95/p99 по шаблонам маршрутов,
   первый токен по режиму, ходы/инструменты/фоллбэки, корпоративные вызовы, outbox, SSE, AI-крон.
4. Pending/failed backlog и возраст старейшего невыполненного события включают backoff/dead;
   после обработки gauges сбрасываются. Имена тем/задач и исходы — ограниченные labels.
5. Правила отмечают фоллбэки >10%, ошибки инструментов/corp-mock, outbox >5 мин, новые dead,
   очередь failed, повторы Kafka, устаревший снимок, недоступность scrape и p95 локальных HTTP >1 с.
   SSE/LLM/внешние вызовы из последнего порога исключены. Внешняя доставка алертов — через будущий Alertmanager.
6. Grafana/Prometheus доступны только на loopback 3005/9095; worker metrics наружу не публикуются,
   nginx возвращает 404 для `/api/metrics`.

## Сценарий 2. Продуктовые показатели

1. «Орби — польза» показывает вопросы, долю без наставника, решения карточек, созданные/решённые
   заявки, эскалации, оценки и выполненные шаги, с пометкой о синтетических данных.
2. Событийные панели используют выбранный интервал; сводные — последние 30 дней и исходные формулы
   API. Вопрос — поиск знаний, не уникальное сообщение; доля — оценка, не доказательство эффекта.
3. Источники эскалаций/доступов/плана совпадают с API, включая сид. NULL при отсутствии знаменателя;
   завершение шага и текущее состояние плана не смешиваются.
4. Роль Grafana имеет SELECT только на безопасные представления без id и свободного текста.
   Чтение `users`, аналитики и остальных сырых таблиц, DML и DDL запрещены.
5. Upgrade/downgrade создают/удаляют views и роль. Init включает LOGIN и создаёт runtime-пароли
   без секретов в репозитории; повторный init сохраняет пароли.

## Сценарий 3. Доставка событий

1. При выключенном флаге бизнес-операция и локальная аналитика работают без брокера.
2. При включённом флаге в одной транзакции сохраняются analytics event и outbox analytics.publish.
   Rollback отменяет обе записи, обращений к Kafka до commit нет.
3. Envelope v1 содержит стабильный event_id/occurred_at, известное имя, HMAC актора либо null,
   разрешённые enum/int/bool и is_synthetic=true. Исходный UUID, текст и произвольные properties не уходят.
4. Изолированный цикл воркера публикует JSON с ключом event_id; idempotent producer и timeout.
   Ошибка → pending с backoff до 1 ч без потери; остальные задачи продолжаются. Отключение флага
   сохраняет очередь. Повтор после неопределённого ACK сохраняет envelope/event_id.
5. Потребитель-пример сохраняет уникальный event_id в SQLite до commit offset; повтор и рестарт
   не создают новый результат. Чужая схема не подтверждается. Это имитация интеграции, не Clickstream Авито.

## Проверка

- Unit: фильтрация значений, HMAC/стабильность, настройки, таймаут/cleanup адаптера, фейковый продюсер,
  успех/retry, дедупликация после рестарта, порядок commit offset, gauges/сбросы, метрики задач/SSE.
- Integration: настоящий Postgres/Redis, атомарность и rollback, выключенный флаг, недоступный брокер,
  восстановление и стабильный id, grants и login роли, совпадение формул сводки, миграции туда/обратно.
- Конфигурация: Compose для обоих профилей, YAML/JSON, SQL всех provisioned панелей под ролью Grafana;
  promtool и живой брокер проверяются отдельно.
