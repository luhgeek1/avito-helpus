## D-001. Бэкенд на Python 3.13 + FastAPI по шаблону монолита (14.11.2026)

Go не обязателен (№52–53, чат 11.11), оценивается совместимость архитектуры. Берём проверенный шаблон
монолита: слои `api → service → domain`, Unit of Work, outbox и воркер, RFC 7807, mypy --strict,
интеграционные тесты на настоящих Postgres и Redis. Python есть в стеке Авито, экосистема AI-агентов
в Python самая зрелая. Postgres и Redis совпадают со стеком Авито.
Отвергли: Go (переписывать паттерны шаблона дольше и рискованнее, AI-экосистема беднее).

## D-002. Агент на Pydantic AI v2, а не LangGraph (14.11.2026)

Авито не раскрывает свой агентный фреймворк; публично названы только «агенты с промптами и MCP»,
AI-крон и feature flags. Наши сценарии — заранее известные цепочки шагов, их надёжнее держать
детерминированным кодом внутри инструментов, а жизненный цикл заявок — в домене и outbox
(согласование приходит веб-хуком через часы, вне запуска агента). Сильная сторона LangGraph —
графы с чекпоинтами — здесь не нужна.
Pydantic AI даёт: тот же pydantic, что и шаблон, типизацию под mypy --strict, зависимости через
`RunContext[Deps]`, нативное подтверждение инструментов (`ApprovalRequired`, deferred tools),
`FunctionModel` для тестов и офлайн-режима, `FallbackModel` для отказоустойчивости, эмбеддинги,
MCP, OpenTelemetry.
Отвергли: LangGraph (лишний слой для наших сценариев, типизация слабее, наблюдаемость тянет к
LangSmith), OpenAI Agents SDK (привязка к провайдеру), самописный цикл (изобретение велосипеда).

## D-003. Модели OpenAI, один ключ для жюри (14.11.2026)

Основная модель агента `gpt-5.4-mini`, тяжёлые фоновые задачи (поиск противоречий, сводки) — `gpt-5.4`.
Эмбеддинги `text-embedding-3-large` с размерностью 1024. Все вызовы — через OpenAI-совместимый API
(`LLM_BASE_URL`), поэтому подойдёт OpenRouter, GigaChat-совместимый шлюз или Ollama.
Жюри нужен один ключ (`LLM_API_KEY`). Без ключа работает офлайн-режим с пометкой в интерфейсе,
поиск — только полнотекстовый.
Отвергли: эмбеддинги Gemini (второй провайдер = второй ключ у жюри), локальные эмбеддинги в образе
(тяжёлый образ, медленный CPU-инференс).

## D-004. Подтверждение действий: нативный HITL + доменное исполнение (14.11.2026)

Инструмент с побочным эффектом сначала проверяет права и исключения, затем бросает `ApprovalRequired`
с карточкой (что именно уйдёт в сервис). Запуск агента завершается, карточка сохраняется как
`pending_action` с истечением срока. Решение пользователя приходит отдельным запросом
(`POST /chat/conversations/{id}/actions/{action_id}`), агент продолжает запуск с `DeferredToolResults`.
При исполнении инструмент снова проверяет права, создаёт заявку с ключом идемпотентности
`tool_call_id` и кладёт событие в outbox; первая отправка в сервис выполняется сразу тем же
идемпотентным обработчиком, повторы — воркером. Каждое решение пишется в аудит.
История диалога хранится на сервере, клиент присылает только новый текст или решение по карточке:
клиент не может подделать аргументы инструмента или «одобрение».

## D-005. Корпоративные сервисы — отдельный MCP-сервер `corp-mock` (14.11.2026)

Имитации сервисов доступов, отсутствий, IT-поддержки, календаря, справочника и мессенджера живут в
отдельном сервисе с MCP-интерфейсом (streamable HTTP), как советуют организаторы. Бэкенд — MCP-клиент
через порт `CorpServices`; замена на реальную интеграцию — новый адаптер того же порта. Статусы заявок
mock присылает веб-хуком с HMAC-подписью; воркер дополнительно сверяет зависшие заявки. Поведение
детерминированное, есть переключатель сбоев для демонстрации ошибок. Код mock исключён из покрытия (№72).

## D-006. Протокол чата: REST + SSE в формате AI SDK UI message stream (14.11.2026)

Ответ агента стримится через SSE чанками формата Vercel AI SDK v6 (`text-delta`, `tool-*`,
`data-*`), поэтому фронтенд может использовать `useChat` со своим транспортом или читать поток
вручную. Свои части: `data-sources`, `data-action`, `data-request`, `data-escalation`, `data-status`.

## D-007. Поиск: Postgres FTS + pgvector, ACL до ранжирования (14.11.2026)

Гибридный поиск в одной базе: полнотекстовый (`russian`) и векторный (pgvector, HNSW), объединение
через Reciprocal Rank Fusion. Фильтр видимости (компания/команда, роли) применяется в SQL до
ранжирования, поэтому закрытое не попадает ни в ответ, ни в контекст модели. Без ключа — только FTS.

## D-009. Демо-учётки вместо регистрации (14.11.2026)

В Авито сотрудники приходят из корпоративного SSO, поэтому регистрации нет. Пользователи создаются
сидом, вход — по email и паролю шаблона (JWT RS256 + refresh в httpOnly-cookie). Тестовые учётки
перечислены в README. Ключи JWT генерируются при первом запуске контейнером `migrate`.
