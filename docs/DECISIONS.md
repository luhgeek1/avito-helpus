## D-001. Бэкенд на Python 3.13 + FastAPI по шаблону монолита (14.11.2026)

Go не обязателен (№52–53, чат 11.11), оценивается совместимость архитектуры. Берём проверенный шаблон
монолита: слои `api → service → domain`, Unit of Work, outbox и воркер, RFC 7807, mypy --strict,
интеграционные тесты на настоящих Postgres и Redis. Python есть в стеке Авито, экосистема AI-агентов
в Python самая зрелая. Postgres и Redis совпадают со стеком Авито.
Отвергли: Go (переписывать паттерны шаблона дольше и рискованнее, AI-экосистема беднее).

## D-002. Агент на Pydantic AI v2, а не LangGraph (14.11.2026)

Авито не раскрывает свой агентный фреймворк; публично названы только «агенты с промптами и MCP»,
AI-крон и feature flags. Наши сценарии — заранее известные цепочки шагов, их надёжнее держать
детерминированным кодом внутри инструментов, а жизненный цикл заявок — в домене и outbox
(согласование приходит веб-хуком через часы, вне запуска агента). Сильная сторона LangGraph —
графы с чекпоинтами — здесь не нужна.
Pydantic AI даёт: тот же pydantic, что и шаблон, типизацию под mypy --strict, зависимости через
`RunContext[Deps]`, нативное подтверждение инструментов (`ApprovalRequired`, deferred tools),
`FunctionModel` для тестов и офлайн-режима, `FallbackModel` для отказоустойчивости, эмбеддинги,
MCP, OpenTelemetry.
Отвергли: LangGraph (лишний слой для наших сценариев, типизация слабее, наблюдаемость тянет к
LangSmith), OpenAI Agents SDK (привязка к провайдеру), самописный цикл (изобретение велосипеда).

## D-003. Модели OpenAI, один ключ для жюри (14.11.2026)

Основная модель агента `gpt-5.4-mini`, тяжёлые фоновые задачи (поиск противоречий, сводки) — `gpt-5.4`.
Эмбеддинги `text-embedding-3-large` с размерностью 1024. Все вызовы — через OpenAI-совместимый API
(`LLM_BASE_URL`), поэтому подойдёт OpenRouter, GigaChat-совместимый шлюз или Ollama.
Жюри нужен один ключ (`LLM_API_KEY`). Без ключа работает офлайн-режим с пометкой в интерфейсе,
поиск — только полнотекстовый.
Отвергли: эмбеддинги Gemini (второй провайдер = второй ключ у жюри), локальные эмбеддинги в образе
(тяжёлый образ, медленный CPU-инференс).

## D-004. Подтверждение действий: нативный HITL + доменное исполнение (14.11.2026)

Инструмент с побочным эффектом сначала проверяет права и исключения, затем бросает `ApprovalRequired`
с карточкой (что именно уйдёт в сервис). Запуск агента завершается, карточка сохраняется как
`pending_action` с истечением срока. Решение пользователя приходит отдельным запросом
(`POST /chat/conversations/{id}/actions/{action_id}`), агент продолжает запуск с `DeferredToolResults`.
При исполнении инструмент снова проверяет права, создаёт заявку с ключом идемпотентности
`tool_call_id` и кладёт событие в outbox; первая отправка в сервис выполняется сразу тем же
идемпотентным обработчиком, повторы — воркером. Каждое решение пишется в аудит.
История диалога хранится на сервере, клиент присылает только новый текст или решение по карточке:
клиент не может подделать аргументы инструмента или «одобрение».

## D-005. Корпоративные сервисы — отдельный MCP-сервер `corp-mock` (14.11.2026)

Имитации сервисов доступов, отсутствий, IT-поддержки, календаря, справочника и мессенджера живут в
отдельном сервисе с MCP-интерфейсом (streamable HTTP), как советуют организаторы. Бэкенд — MCP-клиент
через порт `CorpServices`; замена на реальную интеграцию — новый адаптер того же порта. Статусы заявок
mock присылает веб-хуком с HMAC-подписью; воркер дополнительно сверяет зависшие заявки. Поведение
детерминированное, есть переключатель сбоев для демонстрации ошибок. Код mock исключён из покрытия (№72).

## D-006. Протокол чата: REST + SSE в формате AI SDK UI message stream (14.11.2026)

Ответ агента стримится через SSE чанками формата Vercel AI SDK v6 (`text-delta`, `tool-*`,
`data-*`), поэтому фронтенд может использовать `useChat` со своим транспортом или читать поток
вручную. Свои части: `data-sources`, `data-action`, `data-request`, `data-escalation`, `data-status`.

## D-007. Поиск: Postgres FTS + pgvector, ACL до ранжирования (14.11.2026)

Гибридный поиск в одной базе: полнотекстовый (`russian`) и векторный (pgvector, HNSW), объединение
через Reciprocal Rank Fusion. Фильтр видимости (компания/команда, роли) применяется в SQL до
ранжирования, поэтому закрытое не попадает ни в ответ, ни в контекст модели. Без ключа — только FTS.

## D-010. Responses API для OpenAI, Chat Completions для совместимых шлюзов (14.11.2026)

На живом прогоне OpenAI вернул 400: у моделей GPT-5 параметр `reasoning_effort` вместе с инструментами
в Chat Completions не поддерживается. Для OpenAI используем Responses API, `reasoning_effort=none` по
умолчанию: ответ с вызовом инструмента ≈ 2,5–3,5 с против ≈ 6,5 с с `low`, качество на наших
сценариях то же. Для `LLM_BASE_URL` (OpenRouter, Ollama, шлюзы) — обычный Chat Completions без
параметров рассуждения. Переключается `LLM_API` и `LLM_REASONING_EFFORT`.

## D-011. Деградация вместо отказа при недоступном сервисе (14.11.2026)

Если сервис доступов не отвечает на проверке текущих прав, карточка всё равно показывается с
предупреждением, заявка сохраняется и уходит через outbox, когда сервис оживёт. Отказ сервиса по
существу (`refused`) не повторяется и сразу помечает заявку `failed` с причиной. Истёкшие и
перебитые карточки закрываются как отклонённые перед следующим запуском агента.

## D-012. Один стек на домашнем сервере, nginx на входе (14.11.2026)

**Что.** `avito.prooood.ru` обслуживает весь стек одним Coolify Service: портал, API, воркер, corp-mock, Postgres с
pgvector, Redis. Публичный сервис `web` — nginx на 3000, он раздаёт портал (`site`) и проксирует `/api`. Один workflow
проверяет, собирает четыре образа и деплоит `main`. Конфигурация — `deploy/home/`.

**Почему.** Один origin: куки, CSRF и SSE работают без CORS. Домен в Coolify уже привязан к сервису `web:3000`, так что
публичный сервис остался под тем же именем и менять домен не пришлось. Каждый коммит собирает все образы, поэтому
любой SHA можно выкатить и откатить. Бэкенд стартует в `APP_STAGE=prod`, секреты генерирует Coolify.

**Отвергли.** Rewrites в Next.js: хуже для SSE и привязывают API к рантайму портала. Отдельный домен для API: CORS и
ещё одна DNS-запись. Сборка образов только по изменённым путям: деплой SHA без образа падает.

**Риски.** Сервер в России: OpenAI может быть закрыт по региону, поэтому по умолчанию офлайн-режим, а ключ и шлюз
задаются на сервере. Память: стек укладывается примерно в 1,7 ГиБ лимитов, реально занимает около 0,9 ГиБ.

## D-013. Весь фронтенд — на Tailwind CSS (14.11.2026)

**Что.** Стили фронтенда пишутся только утилитами Tailwind в TSX. Единственный CSS-файл — входной
`frontend/app/globals.css` (`@import "tailwindcss"` и `@config`); тема, палитры, keyframes и базовые
правила — в `frontend/tailwind.config.ts`. Условные классы собираются через `cx` (tailwind-merge).
Inline-стили допустимы только для значений времени выполнения: координаты спутника и меню, палитра
выбранного пета, задержки кадров, прогресс, размеры из числовых props. Статические значения
переведены в классы: `Skeleton` и `Cover` принимают `className` вместо `height`/`radius`/`ratio`,
иллюстрация на обложке — `h-[84%]`/`h-[78%] mt-[18%]`, блокировка прокрутки — `overflow-hidden` на `body`.

**Почему.** Один способ стилизации: состояние видно в разметке, tailwind-merge снимает конфликты
классов, нет мёртвого CSS. Проверка `@tailwindcss/node` подтверждает, что каждый класс в `className`
и `cx` даёт CSS, кроме маркер-классов для JS-селекторов (список — в `frontend/README.md`).

**Отвергли.** CSS Modules и CSS-in-JS — второй способ стилизации рядом с Tailwind. Перевод размеров
аватаров и иконок в фиксированные классы — размер и шрифт считаются из числового prop.

## D-014. Мониторинг отдельным профилем Compose (14.11.2026)

**Что.** Профиль `observability`: Prometheus 3.16.0 и Grafana 13.3.0 с datasource, двумя дашбордами
и правилами алертов из файлов. Порты 9095/3005 привязаны к 127.0.0.1, worker:9100 остаётся внутренним.
Метрики API и отдельного процесса воркера собираются независимо. Низкая кардинальность: enum тем,
фиксированные имена задач (`task`, чтобы не конфликтовать с scrape-label `job`), состояния и исходы;
неизвестное — `other`. Gauge backlog включает pending и dead (на дашборде failed), возраст — все
невыполненные события, в том числе ожидающие backoff; свежесть снимка контролируется отдельно.

**Почему.** Базовый запуск для жюри не требует мониторинга. Воркеров нельзя наблюдать через реестр
API-процесса. Порог кейса <1 с применяется к локальным операциям; SSE и внешние вызовы исключены
из этого алерта. Длительности HTTP в техническом дашборде явно означают полный ответ.
У существующего ассистента error payload и не-dict результат оба помечены `info`; учитываем
`error|info` как консервативный диагностический сигнал и называем это в алерте/инструкции, не
меняя параллельно разрабатываемый код ассистента. У corp-mock учитываем также timeout/unavailable.

**Отвергли.** Обязательный мониторинг при каждом старте; проброс worker metrics наружу; multiprocess
registry между разными контейнерами; labels из id, payload и свободного текста. Внешние уведомления
не отправляем: для продакшена подключается Alertmanager. Анонимный Viewer — только локальное демо.

## D-015. Grafana через безопасные представления и отдельную роль (14.11.2026)

**Что.** Обратимая миграция создаёт роль `orbi_grafana` без LOGIN/пароля и grants SELECT только на
`analytics_dashboard_events` и `analytics_dashboard_summary`. Первая проекция исключает id и
произвольные properties, оставляя разрешённые enum; вторая повторяет формулы и источники
`/analytics/summary?days=30`. План берётся целиком, эскалации — из текущего состояния, как в API.
Профильный init генерирует пароли в volume и включает LOGIN. Роль имеет default read-only и timeout;
на `users`, `analytics_events`, аудит, заявки и остальные исходные таблицы grants нет.

**Почему.** SQL datasource позволяет выполнять произвольный SQL, поэтому ограничение обеспечивается
Postgres, а не запросами панелей. Безопасные представления позволяют сохранить формулы API, не
раскрывая сотрудников/текст и не выдавая доступ к исходным таблицам. Миграция работает и на существующей
БД, тогда как `/docker-entrypoint-initdb.d` запускается только на пустом volume. Пароли отделены от
миграций и не попадают в git. Миграция требует CREATEROLE; в нашем Compose это postgres.
При конфликте с существующей одноимённой ролью миграция останавливается, чтобы не переиспользовать
чужие полномочия в общем кластере.

**Отвергли.** Суперпользователь в Grafana; SELECT на всю схему; доступ к сырому JSON событий;
пароль в migration/provisioning; восстановление текущих SLA/эскалаций только из событий (сид и закрытия
не обязаны порождать полный исторический поток). Downgrade удаляет views и роль в выделенном
демо-кластере; после повторного upgrade init запускается заново.

## D-016. Apache Kafka KRaft и изолированный экспорт outbox (14.11.2026)

**Что.** Профиль `clickstream`: Apache Kafka 4.4.0, один совмещённый broker/controller, репликация 1,
постоянный volume, топик `buddy.analytics.v1` с 3 partitions и retention 7 дней. Асинхронный адаптер
aiokafka за портом `AnalyticsPublisher`, idempotent producer и ограниченный таймаут ожидания.
`CLICKSTREAM_ENABLED=false` по умолчанию; API не создаёт Kafka-клиент. При включении event и outbox
пишутся одной транзакцией; отдельный цикл воркера доставляет только analytics, batch=1. Ошибки
повторяются без перевода аналитики в dead, backoff 2,4,8… с до часа. Выключение флага приостанавливает
уже накопленную очередь; пропущенные во время выключения события автоматически не backfill-ятся.

**Почему.** Кейс прямо называет Apache Kafka; официальный образ и KRaft не требуют ZooKeeper.
Изоляция цикла не даёт отказу аналитики задерживать корпоративные заявки и AI-крон. Доставка
at-least-once: повтор после неопределённого результата публикации сохраняет event_id. Пример
потребителя коммитит SQLite UNIQUE(event_id) перед Kafka offset, переживает дубли и перезапуски.
Это имитация интеграции, не настоящий Clickstream Авито; в продакшене меняются кластер, ACL/TLS/SASL,
секреты и контракт приёмника. Один узел не обеспечивает отказоустойчивость брокера.

**Отвергли.** Redpanda (для демонстрации совместимости достаточно официального Apache Kafka);
синхронный клиент/публикацию из HTTP-транзакции; ожидание Kafka в depends_on у API/воркера;
удаление событий после временного отказа; заявления об exactly-once между Postgres и Kafka;
дедупликацию только в памяти.

## D-017. Неизменяемый обезличенный envelope v1 (14.11.2026)

**Что.** Envelope: schema_version, event_id исходной строки аналитики, name, occurred_at, actor,
properties, is_synthetic=true. Kafka key = event_id. actor = HMAC-SHA256 с отдельным постоянным
случайным секретом из Settings и namespace `orbi.analytics.v1`; системный актор — null.
Allowlist свойств и значений задаётся для каждого типа события: enum, ограниченные int и bool.
Текст, идентификаторы сообщений/ресурсов, slug, email, URL, вложенные списки/объекты не экспортируются.
Envelope сохраняется сразу, повтор не зависит от изменения/удаления пользователя или ротации секрета.

**Почему.** Одна транзакция обеспечивает атомарность; фиксированный envelope даёт стабильную
дедупликацию и не раскрывает исходный user id. Разрешать только имена свойств недостаточно:
произвольный текст может находиться даже в поле с ожидаемым именем.

**Отвергли.** Обычный hash UUID без секрета; новый event_id при retry; пересборку payload из текущих
данных при доставке; экспорт всех properties или чёрный список известных полей ПДн. В локальном
Clickstream сохраняются только event_id, name и occurred_at; actor/properties не пишутся в логи.

## D-018. Windows и одинаковая проверка запуска (14.11.2026)

**Что.** `tzdata` — зависимость backend и corp-mock на Windows. Даты API и календаря показываем
в `Europe/Moscow`, хранение остаётся UTC. Проверка POSIX-прав ключа выполняется только на POSIX;
на всех платформах проверяется работоспособная неизменяемая пара. Worker поддерживает Windows
без `loop.add_signal_handler`. `.gitattributes` фиксирует LF для Docker-входов, `.dockerignore`
исключает локальную `.venv` обеих Python-частей. Smoke использует стандартную библиотеку Python;
shell проверяет реальный интерпретатор и не принимает заглушку Microsoft Store.

**Почему.** Жюри может клонировать проект с `core.autocrlf=true`, без make и системной tz-базы.
HTTP/SSE-ошибка должна давать ненулевой код smoke, отсутствие карточки проверяется через состояние
доступа/заявки. README содержит эквиваленты make для PowerShell.

**Отвергли.** Проверку NTFS как chmod 0600; успешный smoke после ошибки pipeline; копирование
Windows `.venv` поверх Linux-окружения образа; замену tz-базы самодельным часовым смещением.

## D-019. Идентичность заявки и подтверждённая отмена (14.11.2026)

Нумерация с суффиксом заменена D-022; остальные решения этого раздела сохраняются.

**Что.** Создания сериализуются по сотруднику; ключ проверяется вместе с владельцем и видом заявки.
Столбец ключа расширен до 256: клиентские 128 символов должны помещаться вместе с namespace API.
Внешний номер резервируется advisory lock до записи. Коллизия — постоянная ошибка с причиной и
уведомлением, а не сетевой retry; незавершённая старая запись тоже становится неопределимой и failed.
В mock номер включает суффикс ключа; ответы/веб-хуки несут ключ, API сверяет его и тип сервиса.
Старый контракт без ключа поддержан, терминальные решения не перезаписываются.
Перед отправкой очереди повторно проверяются блокировка сотрудника и текущие права на ресурс/уровень.
Перед отменой или напоминанием повторно сверяется идентичность внешней заявки. Напоминание доступно
для access, у остальных сервисов нет такой операции: API возвращает 409 вместо обещания без действия.

Отмена отправленной заявки и напоминание доставляются через outbox. До ответа отмена сохраняет
`submitted` с `payload.cancel_requested` и пояснением: отменённым считается результат сервиса.
Если согласование опередило отмену, сохраняется согласование. Напоминания дедуплицируются в mock;
при отказе доставки приходит уведомление. Сбой dead-handler оставляет событие доступным для повтора.
Сверка переживает отсутствие заявки после сброса. Завершение старой заявки не закрывает шаг,
к которому уже привязана новая. Для сброса демо скрипт останавливает производителей до сброса обеих сторон.

**Почему.** Две системы нельзя атомарно сбросить общей транзакцией. Нельзя связывать чужое решение
по повторно выданному номеру, бесконечно повторять постоянную ошибку или обещать отмену до ответа.

**Отвергли.** Снятие уникальности external_id; молчаливое объединение записей; локальную отмену,
после которой mock всё ещё выдаёт доступ; сброс только одной стороны при работающем worker.
Downgrade с ключами длиннее 128 останавливается без потери данных: перед откатом нужно завершить
или убрать такие демо-записи, а не обрезать ключи и потерять идемпотентность.

## D-020. Контекстные права и срок жизни SSE (14.11.2026)

**Что.** Деликатные вопросы скрыты в деталях, счётчиках и сводке наставника от всех, кроме автора,
назначенного получателя и администратора. Отчёт о противоречии проверяет ACL обеих инструкций
перед созданием эскалации. SSE ограничивает очередь и повторно проверяет токен/версию авторизации
перед передачей данных; при потере авторизации отправляет `auth.required` и закрывается.
Неверное тело подписанного веб-хука даёт RFC 7807 / 422; нечисловые и бесконечные timestamp
отклоняются. Неизвестная заявка и несовпадение сервиса/ключа игнорируются без раскрытия данных.

**Почему.** Право смотреть прогресс подопечного не даёт права читать его обращение к HRBP.
Открытый поток не должен продолжать выдачу после выхода со всех устройств или истечения JWT.

**Отвергли.** Только RBAC без контекста, раскрытие закрытых документов через эскалацию,
однократную проверку авторизации на всё время SSE и 500 для ошибки внешнего контракта.

## D-021. Содержимое знаний оценивается отдельно от поиска (14.11.2026)

**Что.** Добавлены синтетические инструкции по CI и БД, кодстайлу, проверке LLM-кода и доступам;
открытый Playbook пересказан со ссылкой и отделён от демо-регламентов. Для десяти новых вопросов
проверяются документ и нужный раздел; сохранён старый набор. Офлайн eval: recall@5 0,30 → 1,00,
MRR@5 0,25 → 1,00, section recall@5 0,10 → 1,00. Код поиска не менялся.

**Почему.** Попадания вводного абзаца недостаточно для ответа. Эти метрики проверяют конкретный
синтетический корпус, а не доказывают качество на всех вопросах или пользу реальной компании.

**Отвергли.** Подгонку ранжирования в зоне другого участника, вымышленные официальные регламенты
и инструкцию по командировкам: этот вопрос оставлен для демонстрации передачи наставнику.

## D-022. Короткие номера и отдельный сохраняемый счётчик (14.11.2026)

**Что.** Новые номера снова имеют вид `ACC-1042`, `ABS-2101`, `IT-3301`, без суффикса ключа.
Рядом с `CORP_STATE_FILE` хранится отдельный checkpoint `state.sequences.json`: следующий номер
каждого сервиса записывается атомарно с flush/fsync до возврата заявки. Обычный `demo_reset`
очищает бизнес-данные, сохраняя счётчики, в том числе после перезапуска и удаления state.json.
При восстановлении берётся максимум checkpoint, счётчиков снимка и числовых частей его заявок.
Старые длинные номера не переписываются: чтение и повтор по прежнему ключу продолжают работать.
Повреждённый checkpoint останавливает запуск. Хранилищем владеет один процесс mock.

Согласованный `deploy/reset_demo.py` останавливает API/worker, сначала пересоздаёт данные API,
затем вызывает mock с `reset_sequence=true` и запускает производителей. Только этот явный режим
откатывает счётчики к демо-началу; первая заявка Ани — `ACC-1042`. При сбое API/worker не запускаются.
Новый пустой стек также начинает с этих номеров. Потеря всего тома mock вместе со счётчиками
при сохранённой БД API остаётся рассинхронизацией: неизвестную историю восстановить нельзя.
Проверка ключа и постоянная коллизия → failed/уведомление без retry на стороне API сохранены.

**Почему.** Номер должен быть удобен стажёру и совпадать со спецификацией и демо-сценариями.
Отдельный checkpoint не зависит от очищаемого списка заявок; резервирование до ответа допускает
пропуски после сбоя, но не повторную выдачу сохранённого номера. Начальные демо-значения можно
вернуть только после удаления старых заявок API.

**Отвергли.** Хеш в видимом номере (регрессия UX), время/случайную эпоху (длинные числа и зависимость
от часов), откат счётчика при обычном reset и обещание восстановить историю после удаления всех копий.

## D-023. Фронтенд ходит в API напрямую, токен в памяти (14.11.2026)

Портал остаётся на моках MSW для декоративных разделов, а всё про стажёра идёт в настоящий
`/api/v1`: в Docker его маршрутизирует nginx, в `npm run dev` — rewrites Next.js (`ORBI_BACKEND_URL`).
Access-токен живёт только в памяти, refresh — httpOnly-cookie, обновление одно на все параллельные
запросы с заголовком CSRF. При смене учётки кэш запросов, диалог и поток `/events` сбрасываются.
Чат — свой стор (Zustand) поверх ручного чтения AI SDK UI message stream: карточки подтверждения и
наши `data-*` части проще держать в своей модели, чем подстраивать `useChat`.
Сжатие в Next выключено: gzip буферизовал проксируемый SSE до конца потока (нашли на живом прогоне,
уведомления не доходили). В Docker сжимать может nginx.
Отвергли: токен в localStorage (XSS), `EventSource` для `/events` (не умеет заголовок авторизации),
`@ai-sdk/react` (лишняя зависимость ради разбора уже простого протокола).

## D-024. Покрытие фронтенда считаем по всем файлам `src` (14.11.2026)

Раньше Vitest считал только файлы, которые импортировали тесты, — цифра выглядела выше реальной.
Теперь `coverage.include = src/**`, поэтому в отчёте весь код петов и спутника. Тесты используют
записанные ответы и потоки настоящего бэкенда (`frontend/tests/orbi/fixtures`), поэтому контракт
проверяется на реальных данных, а не на придуманных.
