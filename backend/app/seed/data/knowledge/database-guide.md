Тестовая инструкция, не регламент Авито. Пути и пространства вымышлены для прототипа.

## Где документация по базам данных
Документация по работе с базами данных находится в Confluence команды: раздел «Разработка →
Базы данных». В README конкретного сервиса ищи схему, владельца таблиц, локальный запуск,
команды тестов и миграций; история изменений схемы — в каталоге migrations репозитория.
Для «Объявлений» начни с README listings-api и попроси наставника показать схему тестового стенда.
Если страница закрыта, запроси чтение у её владельца; доступ ко всем пространствам не выдаётся.

## Как применять миграции базы данных
Сначала спроектируй изменение с наставником. Подготовь миграцию вверх и обратный переход,
проверь оба на отдельной локальной базе с синтетическими данными. Новая схема должна работать
с текущей и следующей версией сервиса во время выкладки. Долгие блокировки и заполнение новых
полей обсуждай на design review. Команды бери из README сервиса. Не запускай миграции вручную
на production: они проходят ревью и релизный пайплайн ответственным сотрудником.

## Как получить доступ на чтение
Для локальной базы используй тестовые данные. Для dev или аналитики укажи в заявке точный ресурс,
окружение, задачу и минимальный уровень read. Владелец ресурса или DevOps согласует права.
Redash даёт доступ к разрешённым отчётам; он не означает прямой доступ к production PostgreSQL.
Орби покажет карточку доступного ресурса и отправит заявку только после твоего подтверждения.

## Правила работы с продовыми данными
Стажёр не получает прямые права записи в production и не копирует дампы на ноутбук, в таблицы
или внешние LLM. Для отладки попроси наставника подготовить синтетический пример; не пересылай
пароли и connection strings. Даже доступ только на чтение не разрешает выгрузку персональных
данных: используй разрешённые агрегаты. Массовые запросы и изменения выполняет владелец сервиса
по согласованному плану, с ограничениями времени и возможностью отката.
